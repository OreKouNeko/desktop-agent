# 工程手册：一个 GUI Agent 是怎么被做出来的

> desktop-agent v0.1.0b1 · OreKouNeko


这份文档记录构建过程中的关键决策、踩过的坑和验证方法。不是教程，是施工记录。

---

## 一、起点与约束

目标：在 Windows 上用自然语言驱动桌面操作，要求**可控、可验证、可停止**。

硬约束（来自实际使用环境）：

- 磁盘余量紧张 → 不能引入大型本地模型
- 内存只能给 3 GB → 同上
- 不能有明显卡顿 → 拒绝一切全局钩子式方案

由此确定的第一条原则：**不跑本地模型，用系统原生 API + 云端模型**。

---

## 二、架构

```
感知 perception/capture   →  决策 loop + llm   →  动作 actions   →  校验 → 记录
        ↑                                              ↓
   窗口 window                                    刹车 guard
```

四条主线：

1. **能不用模型就不用**：能用无障碍树定位的，绝不发截图；能查缓存的，绝不再问。
2. **每个动作都要有结果**：动作后立即重新采样，比对界面指纹。
3. **高频错误封成原子动作**：`set_cell`、`save_as` 这类组合不该由模型拼。
4. **知识按应用加载**：`profiles.py`，避免提示词互相污染。

## 三、关键实测数据

### 感知成本（同一台机器）

| 应用 | 节点数 | 取树耗时 | 有名字占比 | 判定 |
| --- | --- | --- | --- | --- |
| 记事本 | 44 | 31 ms | 70% | 优 |
| Edge 页面 | 137 | 39 ms | 66% | 优 |
| 系统设置 | 139 | 97 ms | 72% | 优 |
| Electron 应用 | 1823 | 226 ms | 86% | 可用 |
| 微信（Qt） | 4 | — | — | 不可用 |
| DX12 游戏 | 2 | 847 ms | — | 不可用 |

结论：**无障碍树在标准软件上极其划算，在自绘界面上完全没有价值**。所以需要质量评分来决定要不要改走视觉。

### 时间去哪了

| 环节 | 中位耗时 | 占比 |
| --- | --- | --- |
| 模型调用 | 1106 ms | **95%** |
| 感知 | 39 ms | 4% |
| 动作 | 8 ms | 1% |

结论：**优化只应该瞄准"减少调用次数"**，优化感知收益微乎其微。这条结论直接否决了几个后来想做的优化。

## 四、踩过的坑

按严重程度排序，每条都对应真实的失败。

### 1. 全局低级钩子冻结了整个系统（最严重）

**现象**：桌面卡死，任务栏无响应，Win 键无效，只能长按电源。

**原因**：为了检测"用户是否抢过控制权"，安装了 `WH_KEYBOARD_LL` / `WH_MOUSE_LL` 全局钩子。这类钩子在**本进程**里运行，需要 GIL；主线程做纯 Python 重活（图片编码）时握死 GIL，钩子回不来超过 300 ms，Windows 就开始丢弃输入事件。进程若卡住不退出，钩子永远挂着。

**教训**：**监控功能绝不能以牺牲系统输入为代价。** 现在钩子默认关闭，只保留不阻塞输入的 `RegisterHotKey`。

### 2. ctypes 句柄截断（出现三次）

GDI 的 `SelectObject`、剪贴板的 `GlobalAlloc`、钩子回调的 `LPARAM` —— 都是同一类错误：**没声明 `restype/argtypes`，64 位句柄被截成 32 位**。

后果分别是：截图崩溃、写空指针、钩子回调抛异常导致刹车失灵。

**教训**：调用任何 Win32 API 前先写原型，这不是可选项。

### 3. `BoundingRectangle` 不是四元组矩形

UIA 从 COM 返回的是 `(left, top, width, height)`，不是 `(l,t,r,b)`。用错会让所有矩形判断失效，表现为"点击总是偏一点"的玄学 bug。

**教训**：跨 API 边界的数据结构必须用另一个 API 对拍验证（这次是 `GetWindowRect`）。

### 4. 用 SetValue 实现"输入"会毁数据

`type` 动作原本对有 ValuePattern 的控件调用 `SetValue`。但 SetValue 是**整体替换**，于是"在末尾追加一行"实际把原文覆盖了，而测试只检查"包含目标文字"，**给出了假阳性**。

**教训**：动作语义要严格区分（插入 vs 替换）；校验要检查完整状态，不能只查子串。

### 5. 批处理被截断导致死锁

模型一次给 3 步，执行器只跑 2 步就返回，剩下的丢掉。模型下一轮看到状态不符，重新给出同样的 3 步 → 永远循环。

**教训**：**要么完整执行，要么整批拒绝，绝不能静默截断。**

### 6. 一行 return 让模板匹配永久失效

重构"语义匹配"时删掉了一段代码，连带把 `return best[1], best[2]` 也删了。结果 `find()` 永远返回 None，所有任务都绕道走技能选择器——因为选择器能兜住，**功能看起来是好的**，只是慢了、贵了。

**教训**：兜底路径会掩盖主路径的失效。要有针对主路径的断言。

### 7. Unicode 注入丢最后一个字符

Office 里用 `KEYEVENTF_UNICODE` 输入中文，偶发吞掉末尾字符（"任务" 变成 "任务"少了句号）。肉眼几乎看不出来。

**教训**：Office 场景改用剪贴板粘贴；校验要逐字比对而不是"包含"。

### 8. 模态对话框是另一个窗口

另存为对话框、格式确认弹窗都是独立 HWND。智能体盯着主窗口，看不到它们，于是"按了 F12 就当保存好了"。

**教训**：窗口是任务的一部分。现在每步都会检查同进程的新前台窗口并自动跟随。

### 9. UIA 写名称框不触发跳转

用 `ValuePattern.SetValue` 把 `B2` 写进 Excel 名称框，文字变了但 Excel 不做跳转，后续内容贴到随机格子。

**教训**：能"设置值"不等于能"触发行为"。必须像真人那样点进去、敲键盘、回车。

### 10. 提交动作会移动选区

Excel 的 `set_cell` 结尾按回车提交，光标会**下移一格**。所以"写完 A1 再按 Ctrl+B"实际格式化的是 A2。

**教训**：一个动作的副作用（这里是光标移动）会破坏后续动作的前提。最终拆出 `select_cell` 只定位不写入，语义才干净。

**更进一步**：即使选中了单元格，`Ctrl+Shift+5` 这类快捷键偶尔也不生效，而模型会**报告成功**。最终把格式操作做成 `format_cell`：先选中，再去点功能区里那个有名字的按钮。**能点到有名字的控件，就别赌快捷键。**

### 11. 全屏游戏窗口的坐标是假的

DX12 全屏窗口报告的位置在屏幕外（`(167, 1414)`，而屏幕只有 1600 高）。按它换算，每次点击都飞到别处。

**教训**：几何信息不可信时，用"窗口尺寸约等于屏幕"这个特征兜底。

## 五、验证方法

这个项目里最重要的工程习惯：**不相信模型说"我做完了"**。

1. **机器可判定的终态**：Word 解析 docx、Excel 解析 xlsx、PPT 解析 pptx，比对结构而非文字片段。
2. **严格结构校验**：段落列表必须完全相等。宽松的"包含"会放过"多两个空段落"这种隐性损坏。
3. **重复测试**：同一场景连跑多次统计成功率，而不是跑一次算数。
4. **隔离污染**：每次用新文件、重启应用，避免上一个用例的残留。

最终 Office 九类场景：**多轮重复测试 25/25 通过**。

---

## 六、沉淀下来的原则

1. **能不用模型就不用**：模型调用占 95% 的时间，它应该是最后手段。
2. **每个动作都要可验证**：没验证的动作等于没做。
3. **高频组合封成原子动作**：模型的协调能力很弱，一步能做完的不要拆成五步。
4. **知识按上下文加载**：给对的软件看对的规则，别把 Excel 的规则塞给记事本。
5. **宁可拒绝，不要猜**：不确定就退回规划，不要硬闯。
6. **系统的稳定性高于功能**：任何可能影响整机响应速度的机制，默认关闭。

---

## 七、没解决的

- **实时操作**：单步 1–2 秒，比人慢一个数量级，游戏和视频剪辑类做不了。
- **全屏游戏的坐标精度**：视觉模型定位像素不够准，靠坐标点击成功率低。
- **跨应用长流程**：目前能做两三个窗口的简单协作，更长的链路缺少状态管理。
- **复杂排版**：Office 里只覆盖了单元格和段落级操作，样式、表格、图表尚未验证。
